# AI Portal 环境配置与制造业适配说明

## 1 结论

参考文件 `技术选型版本参考.md` 可以作为后续 Python 依赖版本的参考，不能直接当作当前项目的完整环境文件使用。它主要是一份把 LangGraph、模型、RAG、Milvus、文档解析和测试库放在一起的依赖清单，没有包含 Docker 服务连接、日志目录、模型密钥、工厂隔离和制衣业务上传约束。

当前项目采用分阶段环境：基础平台先使用 Python 3.13.15、Node.js 24.21.0、FastAPI、配置、日志和 Docker Compose；数据库、文件存储和 Milvus 的连接参数先写入统一环境模板；LangGraph、Torch、Embedding、Reranker 和本地模型等重量依赖在两个月基础平台验收后再单独加入。

## 2 当前可直接使用的环境

将 `infra/.env.example` 复制为 `infra/.env` 后，可以直接用于本地 Compose 配置检查和基础服务启动：

```powershell
Copy-Item infra/.env.example infra/.env
docker compose --env-file infra/.env -f infra/docker-compose.yml config --quiet
docker compose --env-file infra/.env -f infra/docker-compose.yml up -d
```

当前模板已经包含：

- PostgreSQL 连接参数，用于用户、部门、权限、任务和业务元数据。
- Redis 连接参数，用于缓存以及后续 Celery 任务队列。
- `AUTH_MODE=demo` 和 JWT/企业 OIDC 占位参数，当前不开放员工自助注册。
- MinIO 业务文件 Bucket 和 Milvus 独立 Bucket 名称。
- Milvus Standalone 和 etcd 的 Docker 内部地址。
- 智谱、通义千问和未来本地模型的占位配置。
- 日志轮转、`X-Request-ID` 和本地日志目录。
- `DATA_ROOT` 数据根目录：本地默认 `../.data`，服务器改为 500 GB 数据盘上的 `/data/ai-portal`。
- 台北制衣试点的公司、地区、工厂默认值和文件类型限制。

本地开发默认使用容器内部主机名，例如 `postgres`、`redis`、`minio` 和 `milvus`。如果从宿主机上的 PyCharm 直接连接服务，必须使用实际暴露的 `localhost` 地址；Milvus 和 etcd 当前没有映射宿主机端口，后端本地调试应优先连接本机 Compose 网络中的后端容器，或后续按需要增加仅限开发环境的端口映射。

## 3 制衣业务适配

环境变量只保存部署级参数和初始默认值，不把部门、工厂和 Agent 权限写死在环境文件中。正式业务数据进入 PostgreSQL，并通过权限服务计算：

| 业务维度 | 首期建议 | 后续扩展 |
| --- | --- | --- |
| 公司 | 浙江惠中制衣有限公司 | 多公司或集团租户 |
| 区域 | `TW`，对应台北试点 | 其他国家和地区 |
| 工厂 | `TAIPEI` | 各地工厂和生产基地 |
| 部门 | 生产、工艺、面料、质量、采购、技术、财务、人事 | 工厂自定义部门 |
| 文件类型 | PI、报价单、发票、BOM、工艺单、质检记录、生产通知 | ERP/MES 导出文件和更多图片格式 |
| 数据范围 | 公司、区域、工厂、部门、知识库和密级 | 项目、产线、订单和客户范围 |

后续数据库应使用稳定的 `company_id`、`region_id`、`factory_id`、`department_id` 和 `knowledge_base_id`，不要使用环境文件中的名称作为权限键。员工调岗、离职和工厂切换都由用户组织数据和 `agent_grants` 处理。

## 4 参考依赖的分阶段处理

| 依赖范围 | 当前是否安装 | 处理方式 |
| --- | --- | --- |
| FastAPI、Uvicorn、Pydantic、multipart、httpx、structlog | 是 | 支撑当前 Portal 骨架、日志和文件接口 |
| SQLAlchemy、asyncpg、Alembic、Redis 客户端 | 下一步 | 接入用户、权限、任务和数据库迁移时锁定版本 |
| pymilvus、文档解析库、SSE | RAG/任务阶段 | 先完成接口契约，再按真实文件样本加入 |
| LangChain、LangGraph、checkpoint-postgres | Agent 设计阶段 | 两个月基础平台验收后，由四人共同设计和接入 |
| transformers、sentence-transformers、FlagEmbedding、Torch | GPU/模型阶段 | 放到独立模型 Worker 或推理容器，不放进轻量 Portal API 镜像 |
| MCP、搜索工具、外部模型 SDK | Agent 工具阶段 | 经过安全、权限和数据外发评审后再启用 |

参考文件中的 `torch==2.5.1` 没有指定 L20 对应的 CUDA Wheel，不能直接拿来部署 GPU 服务器。租用 L20 后，应根据 NVIDIA 驱动和 CUDA 版本单独构建 GPU Worker，并用真实图片、PDF 和业务样本验证显存、延迟、并发和许可证。

## 5 外部模型配置原则

智谱和通义千问的 API Key 只放在服务器 `infra/.env` 或密钥管理服务中，不提交 Git，不进入前端。当前模板默认 `EXTERNAL_MODEL_ENABLED=false`，只有 IT 和业务确认数据外发范围后才能开启。

模型调用必须经过后端 Model Gateway，统一记录模型别名、超时、重试和 `trace_id`。本地开发默认使用 `mock`，接入真实模型前再将 Provider 切换为 `qwen` 或 `zhipu`。财务、技术、客户以及其他敏感文件不能因为路由失败而自动发送给外部模型；没有本地模型或明确授权时应向用户澄清。

## 6 服务器环境调整

目前的 L20 服务器可以作为单机开发、测试和后续 GPU Worker 主机。建议分配：

- 200 GB 系统盘：操作系统、Docker、代码、镜像和必要系统日志。
- 500 GB 数据盘：PostgreSQL、MinIO、Milvus、etcd、模型文件、任务中间文件和备份。
- L20 48G：后续 OCR、意图路由、Embedding、Reranker 或经过评测的本地模型。
- 8 vCPU、64 GB 内存：Portal、数据库、缓存、MinIO、Milvus 和 Worker 的容器资源总和必须设置上限。

生产环境必须替换数据库、MinIO 和模型密钥，设置数据盘容量告警，并将 Milvus、etcd 和管理端口限制在 Docker 内部网络或 VPN 中。

服务器部署前将 `infra/.env` 中的 `DATA_ROOT` 改为 `/data/ai-portal`，并提前创建对应目录及权限。这样 PostgreSQL、Redis、MinIO、etcd 和 Milvus 的持久化数据不会默认占用 200 GB 系统盘。

## 7 使用前检查

```powershell
# 配置检查
docker compose --env-file infra/.env.example -f infra/docker-compose.yml config --quiet

# 后端语法检查
python -m compileall -q backend/app

# 确认敏感配置不在 Git
git status --short
```

目前这套配置适合先搭建制衣企业的基础 Portal 环境；它已经为后续多工厂、知识库、知识图谱、LangGraph Agent 和本地 GPU 模型预留连接参数，但没有把尚未确定的模型和业务权限提前写死。
