# AI Portal 第一阶段项目骨架说明

## 当前定位

当前版本是可运行的 Workflow 优先开发骨架。第一阶段先让员工选择已经授权的工作流并完成一次前后端闭环，后续再把工作流逐步升级为受控多智能体编排。当前不提前实现 Supervisor、自动意图识别和真实企业 SSO。

## 已完成并已同步到 GitHub

- Vue 3、TypeScript、Vite 前端入口和聊天工作台
- FastAPI 模块化单体后端、`/health` 健康检查和结构化日志
- Workflow 目录、详情和运行接口
- 演示员工和平台管理员身份，通过 `X-Demo-User` 切换
- 服务端工作流可见性和执行权限校验，前端不承担权限判断
- 运行记录归属校验：创建者可查看，平台管理员可审计，其他员工不可读取
- 本地开发文件上传、扩展名和大小校验，生产环境预留 MinIO
- PostgreSQL、Redis、MinIO、Milvus Standalone、etcd 的 Compose 编排
- 前后端 Dockerfile、环境变量模板和基础测试
- GitHub 仓库：`https://github.com/zibochuanmei/ai-portal`

## 当前可以验证的链路

1. 员工打开前端，后端返回当前演示身份。
2. 前端加载该身份可以使用的工作流。
3. 员工选择工作流并输入问题，可附加 PDF、Word、TXT 或图片。
4. 前端调用 `POST /api/v1/workflows/{workflow_id}/runs`。
5. 后端返回运行编号、状态和演示结果。
6. 运行结果只能由创建者或平台管理员读取。

当前运行结果仍是模拟数据，运行记录保存在内存中，重启后会清空；这只用于验证前后端接口，不代表生产实现。

## 接下来两个月的开发顺序

1. 固定四台电脑的 Python 3.13.15、Node.js 24.21.0 和 Git 版本，完善分支和代码检查流程。
2. 接入 PostgreSQL、SQLAlchemy 和 Alembic，落地用户、部门、角色、工作流、授权关系和运行记录。
3. 将演示身份替换为 JWT，并保留企业 SSO/OIDC 适配层；在企业认证未提供前不允许自由注册。
4. 将工作流目录、员工授权和运行状态从内存迁移到数据库。
5. 接入 MinIO 和异步任务，完成文件解析、任务重试和失败记录。
6. 接入 Model Gateway，统一适配智谱、通义千问和后续本地模型。
7. 接入 Milvus，建设文档清洗、切分、Embedding、检索和引用链。
8. 选择一个真实业务工作流完成验收，再扩展其他工作流。
9. 在权限校验稳定后，设计受控多智能体编排；Supervisor 只能接收当前用户已授权的工作流集合。

## 当前明确不做

- 不把复杂多智能体编排放在骨架阶段。
- 不把权限判断放在前端，也不允许 Agent 绕过后端权限调用工具。
- 不让业务工作流直接连接 Milvus，统一通过 VectorStoreService 访问。
- 不在代码中写入模型 API Key、数据库密码或服务器私钥。
- 不把最终本地模型型号提前写死。
- 不把内存演示数据误认为生产数据库能力。
