# AI Portal 推荐开发环境配置方案

## 1 推荐结论

针对四台开发电脑、单台 L20 48G 云服务器和制衣企业首期试点，建议采用“本地统一开发环境 + Docker 基础服务 + 云服务器集中测试和 GPU Worker”的方案。

四台电脑负责日常编码、页面开发、接口开发和单元测试；PostgreSQL、Redis、MinIO、Milvus 等基础服务通过 Docker Compose 启动。云服务器用于共享测试环境、脱敏业务样本验证和后续 OCR、Embedding、意图识别等 GPU 任务。生产模型和复杂 Agent 不在第一天部署。

## 2 四台开发电脑

### 2.1 操作系统和工具

| 项目 | 推荐配置 |
| --- | --- |
| 操作系统 | Windows 11 专业版，启用 WSL2 Ubuntu 22.04 或 24.04 |
| IDE | PyCharm 负责 Python 后端；前端可继续使用 PyCharm 或 VS Code |
| Python | 3.13.15（仓库根目录 `.python-version` 已固定） |
| Node.js | 24.21.0（仓库根目录 `.node-version` 已固定），配合 Vue 3、TypeScript 和 Vite |
| Git for Windows | 安装包 2.55.0.5；命令行按 2.55.0 或更高版本校验，统一使用 `main`、`develop` 和功能分支 |
| 容器 | Docker Desktop 稳定版，启用 WSL2 后端和 Compose V2 |
| 磁盘 | 至少保留 100 GB SSD 空间；Docker 数据目录不要放在空间不足的系统盘 |
| 内存 | 16 GB 起步，建议 32 GB |

开发电脑不要求安装 CUDA、Torch、Milvus、PostgreSQL 或 Redis 的本地版本。Python、Node 和基础服务统一通过项目配置或 Docker 使用，避免四个人的环境不一致。

### 2.2 开发机资源建议

Docker Desktop 建议分配 6-8 个 CPU、12-16 GB 内存。日常开发可以只启动 PostgreSQL、Redis、MinIO 和后端；需要检索接口联调时再启动 Milvus 和 etcd。不要在四台电脑上都下载大型本地模型。

## 3 当前项目基础服务

项目当前采用模块化单体和 Docker Compose，建议固定以下服务边界：

| 服务 | 建议版本或方式 | 用途 |
| --- | --- | --- |
| Vue | Vue 3.5.13 + TypeScript 5.7.3 + Vite 6.2.5 | 员工端和管理员端 |
| FastAPI | Python 3.13.15 + FastAPI 0.115.12 + Uvicorn 0.34.0 | Portal API 和权限入口 |
| PostgreSQL | 16 | 用户、部门、权限、任务、审计和业务元数据 |
| Redis | 7 | 缓存和后续异步任务队列 |
| MinIO | `RELEASE.2024-06-13T22-53-53Z` | 制衣业务文件、处理中间文件和备份 |
| Milvus | Standalone 2.4.15 | 后续文档向量检索 |
| etcd | 3.5.5 | Milvus Standalone 元数据依赖 |
| Nginx | 作为前端容器入口 | 统一入口、静态文件和请求追踪 |

PostgreSQL、Redis、MinIO、Milvus 和 etcd 的连接参数已经写入 `infra/.env.example`，后端通过环境变量读取。Milvus 和 etcd 当前只允许 Docker 内部网络访问，不直接暴露到公网。

前后端基础依赖已固定为具体版本，禁止恢复为 `latest` 或宽泛的 `>=` 范围。首次具备网络条件时，在 `frontend` 目录执行 `npm install` 并提交生成的 `package-lock.json`，在 `backend` 目录生成并提交 `uv.lock`（或团队确定的其他 Python 锁文件）；之后团队统一使用锁文件安装，避免传递依赖漂移。当前受限开发环境无法访问 npm 镜像，因此仓库暂未生成锁文件，不能把这一步伪装成已完成。

## 4 项目阶段依赖

参考的依赖清单不建议一次性安装。建议按阶段拆分，避免把 GPU 和 Agent 依赖装进轻量 API 环境：

| 阶段 | 依赖范围 | 使用时间 |
| --- | --- | --- |
| 基础平台 | FastAPI、Uvicorn、Pydantic、multipart、httpx、structlog | 现在 |
| 数据和任务 | SQLAlchemy、asyncpg、Alembic、Redis 客户端、SSE | 用户、权限、任务接口开发时 |
| Agent | LangChain、LangGraph、checkpoint-postgres | 两个月基础平台验收后 |
| RAG | pymilvus、PDF/Word/Excel 解析、Embedding、Reranker | Agent 设计和知识库阶段 |
| GPU Worker | CUDA 对应的 Torch、Transformers、PaddleOCR、FlagEmbedding | L20 服务器评测后 |

GPU 依赖不放进 FastAPI API 镜像。后续使用独立 GPU Worker 或模型容器，通过 Redis 队列或 Docker 内部网络接收任务。

## 5 环境文件和数据目录

### 5.1 开发电脑

提交 Git 的是：

```text
infra/.env.example
```

实际运行的是：

```text
infra/.env
```

本地 `infra/.env` 默认使用：

```text
DATA_ROOT=../.data
```

数据库、Redis、MinIO、etcd 和 Milvus 数据会写入项目根目录的 `.data/`，该目录已加入 `.gitignore`。

四台电脑使用同一份 Compose 文件、同一套镜像版本、同一组环境变量名称和同一个 `COMPOSE_PROJECT_NAME=ai-portal`。每台电脑的数据目录可以保存在本机，不要互相复制数据库目录。Windows Docker Desktop 下大量小文件读写可能较慢，后续可以把 Compose 数据目录迁移到 WSL2 的 ext4 文件系统或改用 Docker 命名卷。

### 5.2 云服务器

服务器使用单独的 `infra/.env`，至少修改：

```text
APP_ENV=test
COMPOSE_PROJECT_NAME=ai-portal
DATA_ROOT=/data/ai-portal
POSTGRES_PASSWORD=替换为强密码
MINIO_ROOT_PASSWORD=替换为强密码
JWT_SECRET=替换为随机密钥
```

500 GB 数据盘建议挂载到 `/data`，并在启动前创建：

```text
/data/ai-portal/postgres
/data/ai-portal/redis
/data/ai-portal/minio
/data/ai-portal/etcd
/data/ai-portal/milvus
/data/ai-portal/models
/data/ai-portal/backups
```

200 GB 系统盘用于操作系统、Docker、代码、镜像和必要日志；500 GB 数据盘用于业务数据、向量索引、模型文件和备份。

首期只有一台云服务器时，先运行共享测试环境。生产环境以后仍使用同一套代码、Compose 文件和服务版本，只单独维护数据目录、数据库、MinIO Bucket、Milvus Collection 前缀和密钥，不能复用测试数据。

## 6 L20 云服务器配置

目前的 L20 48G、8 vCPU、64 GB 内存配置适合首期单机测试和 GPU Worker 验证。服务器建议安装：

1. Ubuntu 22.04 LTS 或云厂商提供的稳定 Linux 镜像。
2. 与云厂商驱动匹配的 NVIDIA Driver。
3. NVIDIA Container Toolkit。
4. Docker Engine 和 Docker Compose V2。
5. Nginx、备份工具和磁盘监控工具。

GPU 服务器先完成 `nvidia-smi`、Docker GPU 容器、OCR 样本、PDF 样本、显存峰值和任务超时测试，再确定本地意图模型、Embedding、Reranker 和视觉模型。不能直接因为显存为 48G 就承诺运行 70B 模型或高并发生产推理。

公网只开放 Nginx 的 80/443 端口。PostgreSQL、Redis、MinIO 管理端、Milvus、etcd 和 GPU 模型端口限制在 Docker 内部网络、VPN 或运维跳板机中。

## 7 制衣业务配置原则

环境变量只提供首期默认值，不把业务权限写死。真实业务数据放到 PostgreSQL：

- 公司和租户
- 国家或地区
- 工厂和生产基地
- 生产、工艺、面料、质量、采购、技术、财务和人事部门
- PI、报价单、发票、BOM、工艺单、质检记录和生产通知等文件元数据
- 知识库范围、密级、Agent 授权和员工在职状态

每条文件和知识库数据后续应关联 `company_id`、`region_id`、`factory_id`、`department_id` 和 `classification`。台北工厂只是首期数据，不应成为代码中的固定判断。

## 8 模型和数据安全

本地开发默认：

```text
MODEL_GATEWAY_DEFAULT_PROVIDER=mock
EXTERNAL_MODEL_ENABLED=false
LOCAL_MODEL_ENABLED=false
```

智谱和通义千问的 API Key 只放服务器环境文件或密钥管理服务，不提交 Git，不进入 Vue 前端。财务、技术、客户和其他敏感文件不能在路由失败时自动发送到外部模型。

开发阶段只使用脱敏的制衣样本，不把真实员工信息、客户信息、订单金额和未授权工艺资料上传到个人电脑或公共模型。

## 9 日志和监控

当前项目已经接入 `structlog + X-Request-ID`：

- 后端日志：`logs/backend/ai-portal.jsonl`
- Nginx 日志：`logs/nginx/`
- Docker 日志：通过 `docker compose logs` 查看

两个月基础平台阶段先保证请求、权限拒绝、任务异常和部署问题可追踪；基础平台稳定后，再增加 Prometheus、Grafana、容器资源监控、队列积压和模型调用指标。

## 10 推荐启动顺序

```powershell
cd C:\Users\liu\.codex\worktrees\1e2f\RAG项目\ai-portal
Copy-Item infra/.env.example infra/.env
docker compose --env-file infra/.env -f infra/docker-compose.yml config --quiet
docker compose --env-file infra/.env -f infra/docker-compose.yml up -d
```

随后在 PyCharm 中创建 `backend/.venv`，安装当前基础依赖并启动 FastAPI；另开终端安装前端依赖并启动 Vue。四个人都按同一份 `.env.example` 和 Compose 文件操作，个人密码和 API Key 只保留在自己的 `.env` 中。
